# 模块解读 06：权限系统 —— 给 Agent 装上安全刹车

> 本文拆解 `autocode/permissions/` 包：
> 权限模式、危险命令检测、路径沙箱、规则引擎如何分层协作，决定一次工具调用是
> allow（放行）/ deny（拒绝）/ ask（问人）。
> 全文基于本项目 `autocode/` 包（模块解读，供自研参考）。

## 1. 模块职责

Agent 有了工具就拥有了「动手能力」，但必须防止它乱来。权限系统是主循环执行工具前的
**唯一关卡**：每个 `ToolCall` 在执行前都要过 `PermissionChecker.check()`，得到一个
`Decision`。是放行就继续；是要问人就 `yield PermissionRequest` 挂起，等用户在 TUI
里批准/拒绝/总是允许。

`permissions/` 包结构：

| 文件 | 职责 |
|------|------|
| `modes.py` | 权限模式枚举 + 「模式 × 工具类别 → allow/deny/ask」矩阵 |
| `checker.py` | `PermissionChecker`：把各层检查按顺序串起来，产出 Decision |
| `dangerous.py` | Bash 命令的危险性检测（黑名单 + 危险子串） |
| `sandbox.py` | 路径沙箱：读写只能落在项目目录内，防 `../` 越权 |
| `rules.py` | 规则引擎：项目级 `permissions.yaml` 自定义规则覆盖默认 |

## 2. 核心数据结构

### 模式 × 类别矩阵（`modes.py`）

```python
DecisionEffect = Literal["allow", "deny", "ask"]

class PermissionMode(str, Enum):
    DEFAULT / ACCEPT_EDITS / PLAN / BYPASS / CUSTOM / DONT_ASK

_MODE_MATRIX = {
    DEFAULT:       {"read": "allow", "write": "ask", "command": "ask"},
    ACCEPT_EDITS:  {"read": "allow", "write": "allow", "command": "ask"},
    BYPASS:        {"read": "allow", "write": "allow", "command": "allow"},
    ...
}
```

工具用 `category`（read/write/command，见 03 章）归类，矩阵按类别给默认态度：
只读放行、写/命令默认要问人。这就是五层防御的第一直觉。

### Decision（`checker.py`）

```python
@dataclass
class Decision:
    effect: DecisionEffect    # allow | deny | ask
    reason: str               # 给用户看的拦截理由
```

### 沙箱（`sandbox.py`）

`PathSandbox(project_root)` 对每个要读写的路径做校验：`resolve()` 后必须落在
`project_root` 内，防止 `../../etc/passwd` 这类越界读。

## 3. 关键流程

### PermissionChecker.check() 的分层判定（`checker.py`）

```
Layer 0  权限模式 PLAN 例外：
         只允许 Agent/ToolSearch/AskUser/ExitPlanMode；
         写/编辑 plan 文件本身放行（plan 是允许改的那个文件）
Layer 1  只读命令自动放行：is_safe_command("git status"...) == True → allow
Layer 1b Bash 危险命令黑名单：detector.detect(cmd) 命中 → deny
Layer 2  路径沙箱：文件类工具读写越界 → deny
Layer 3  规则引擎：permissions.yaml 里显式 allow/deny 命中 → 直接定
Layer 4  模式矩阵兜底：mode_decide(mode, category)
Layer 5  以上都到不了 allow/deny → ask（交给用户，HITL）
```

**分层设计要点**：每层只管一类信号，越靠前的层越「机械」越可信（沙箱、黑名单），
越靠后的层越「主观」（模式默认、用户规则）。规则引擎优先级高于模式默认，用户能精确
覆盖默认行为——例如「`Bash(git *)` → allow」让常见的 git 命令免打扰。

### 主循环如何消费 Decision

```
ToolCallComplete 到达
  → PermissionChecker.check(tool, arguments) → Decision
  → allow   → 执行工具
  → deny    → ToolResultEvent(is_error=True, output="权限规则拒绝: ...") 回填给模型
  → ask     → yield PermissionRequest；挂起等 TUI 的 PermissionResponse
              用户批准 → 执行；拒绝 → 结果回填"用户拒绝了此调用"
```

注意 ask 流程的**可恢复性**：请求被 yield 出来后主循环暂停该工具，等 UI 回调
`PermissionResponse`（approve / deny / allowAlways）再继续——这就是 HITL
（Human-in-the-loop）的实现。

### DangerousCommandDetector（`dangerous.py`）

`detect(command) -> (hit, reason)`：内置一组高危模式（`rm -rf`、`git push --force`、
`curl ... | sh` 等），命中即 deny，reason 展示给用户。只作用于 `command` 类工具。

## 4. 要点小结

1. **为什么权限判断要分层而不是写一个大 if？**
   每个信号独立演进：加一个沙箱规则不影响模式矩阵；项目加一条自定义规则不碰代码。
   且分层有语义顺序——机械性越强的越早定（沙箱越界直接 deny，不值得再问模式）。

2. **`ask`（HITL）是怎么实现的、为什么不阻塞整个循环？**
   `check()` 返回 ask 后主循环 `yield PermissionRequest`，该事件被 TUI 消费弹出确认框；
   同时主循环**暂停在 await 上**等回调。事件驱动让「等人」不烧 CPU、不阻塞其它并发工具。

3. **规则引擎为什么能覆盖模式默认？**
   Layer 3 在 Layer 4 之前：permissions.yaml 命中即返回，根本走不到模式矩阵。这让
   用户能用一条 `Bash(git *)` 规则把「默认 ask」压成「git 全放行」。

4. **PLAN 模式的例外为什么要单独一层（Layer 0）？**
   plan mode 里模型被要求只出不改代码，但 plan 文件本身必须能写——否则方案写不进去。
   所以只放行极少数「元操作」工具 + 对 plan 文件的写入，其余一律先问。

5. **命令被 deny 后模型会怎样？**
   deny 的结果以 `is_error=True` 的 ToolResultEvent 回填给模型，模型看到「用户/权限
   拒绝」，通常换一种做法（改用被允许的工具或命令）。system prompt 里也写了
   「被拒不要原样重试，换思路」。

## 附：五层权限防御一览（常被问「怎么防 Agent 乱来」）

| 层 | 机制 | 管什么 |
|----|------|--------|
| 1 | 模式矩阵 | 三类工具的默认放行/询问态度 |
| 2 | 危险命令黑名单 | Bash 高危命令硬拦截 |
| 3 | 路径沙箱 | 文件读写限定在项目目录 |
| 4 | 规则引擎 | 项目自定义 allow/deny 覆盖默认 |
| 5 | HITL ask | 拿不准的交给用户批准 |
